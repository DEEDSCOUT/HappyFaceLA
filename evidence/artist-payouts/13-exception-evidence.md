# 13 — Exception evidence

Status: **DURABLE EXCEPTION MODEL IMPLEMENTED; OPERATIONAL RECOVERY NOT YET EXERCISED E2E**

The schema stores exceptions without deleting or rewriting the financial obligation. Each entry may bind ledger, batch, artist, Booking, Assignment, reason code, safe reason, required owner action, provider reference, retry timing, status, and resolution evidence.

| Condition                                                                       | Fail-closed behavior                                                                                                                                                                        |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Insufficient available balance/reserve                                          | Stop before claiming a Transfer; require a fresh funding decision.                                                                                                                          |
| Requirements or payout restriction                                              | Refresh current Account, block create, and direct the artist to Stripe-hosted remediation.                                                                                                  |
| Ambiguous Transfer response                                                     | Keep the attempt claimed; search exact provider inventory; never blind-create a replacement.                                                                                                |
| Destination payment not yet available                                           | Keep pending and retry retrieval without inventing Paid state.                                                                                                                              |
| Payout failed/canceled                                                          | Keep Paid false; retain Transfer identity; permit verified later Payout replacement.                                                                                                        |
| Automatic Payout used a bank different from the immutable pre-Transfer snapshot | Keep Paid false and retain the mismatch exception until the owner approves the exact ledger/Payout pair against current Stripe Account, Payout, Transfer, and destination-payment evidence. |
| CRM outage/conflict/readback mismatch                                           | Preserve Stripe evidence, keep `reconciled=false`, and require an authoritative read before retry.                                                                                          |
| Transfer reversal                                                               | Reopen reconciliation and require an owner-approved recovery decision.                                                                                                                      |
| Manual payment                                                                  | Require exact amount/digest/owner phrase/evidence and CRM readback; historical evidence becomes immutable.                                                                                  |

Manual-payment intent cancellation is allowed only when the separately signed CRM read returns the exact expected revision and a pristine `null` payout projection. `{}`, partial, paid, or manual projections are not treated as safe cancellation evidence. The current real Apps Script/server-client regression proves that a missing projection is serialized as signed JSON `null` and survives response verification as the exact null value; this is local server/client evidence, not a deployed copy readback.

A retry after the external manual-payment projection already exists is narrower still: the service admits only the sole exact `EXISTING_PAYOUT_PROJECTION_PRESENT` reason together with the matching durable `MANUAL_REVIEW` intent. A separately signed CRM readback must exactly equal the projection expected from that persisted intent before the same claim is recovered and D1 finalization is retried. Any extra reason, missing/mismatched intent, or readback disagreement stays blocked. A local regression covers the committed-CRM/D1-finalization-failure recovery path.

For a legitimate post-Transfer bank change, the original ledger destination and approval timestamp remain immutable. Only the owner may submit a safe 12–240 character reason and the exact phrase `APPROVE DESTINATION <ledger_id> <payout_id>`. The service derives both bank IDs from durable/authoritative Stripe state, verifies that the exact Payout contains the ledger's destination payment, requires the replacement bank to be the current payout-ready recipient destination, and appends a separate `payout_destination_variance_approvals` row plus financial audit entry. That row binds the environment, ledger, Payout, original and replacement destinations, current recipient approval timestamp, owner, reason, and creation time; database guards prohibit update or deletion. Admin-supplied bank IDs, generic exception resolution, or rewriting the original snapshot cannot authorize `Paid`.

No exception was induced against a Stripe Sandbox or current CRM adapter in this workflow. Operational evidence must include recovery and failure runs, not only happy-path tests.
